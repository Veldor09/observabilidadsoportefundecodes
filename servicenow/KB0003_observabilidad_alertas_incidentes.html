Observabilidad, Alertas y Gestión de Incidentes — Fundecodes Digital

Este artículo describe el stack completo de observabilidad del sistema Fundecodes Digital, incluyendo la recolección de métricas con Prometheus, la visualización en Grafana, las tres alertas configuradas, la integración automática con ServiceNow y las notificaciones a MS Teams. También explica cómo reproducir un incidente controlado con el script de carga.

1. Arquitectura del sistema de observabilidad

El flujo completo de observabilidad funciona de la siguiente manera:

  1. El backend NestJS expone métricas en GET /metrics (formato Prometheus).
  2. Prometheus hace scraping de esas métricas cada 15 segundos.
  3. Grafana consulta Prometheus para mostrar dashboards en tiempo real.
  4. Cuando una alerta se activa en Grafana, envía un webhook al endpoint POST /api/webhooks/alert del backend.
  5. El backend procesa la alerta en paralelo:
    • Crea un incidente en ServiceNow via REST API.
    • Envía una notificación al canal de MS Teams via Power Automate.

3. Levantar Prometheus y Grafana

Todos los componentes de observabilidad se levantan con un único comando desde la carpeta observability/: 

cd observability
docker compose up -d

Verificar que ambos contenedores están corriendo:

docker compose ps

4. Configurar la variable del Webhook de MS Teams

Antes de levantar Grafana por primera vez, o para actualizar el webhook, configurar la variable de entorno en el archivo observability/.env: 

# Crear o editar el archivo .env dentro de observability/

Luego reiniciar Grafana para que tome el nuevo valor: 

docker compose restart grafana

6. Alertas configuradas

El sistema tiene tres alertas definidas en observability/alerts.yml y provisionadas en Grafana:

Alerta 1 — HighHttpErrorRate (warning)

Condición: Más del 10% de las peticiones HTTP retornan errores (4xx o 5xx) durante al menos 1 minuto. 

(
  sum(rate(http_errors_total{app="fundecodes-backend"}[2m]))
  /
  sum(rate(http_requests_total{app="fundecodes-backend"}[2m]))
) > 0.10

Significado operativo: Indica que el sistema está rechazando o fallando al procesar una fracción significativa del tráfico. Puede ser causado por un bug, una ruta inexistente o sobrecarga.

Alerta 2 — HighHeapMemoryUsage (warning)

Condición: El heap de Node.js supera 250 MB de forma sostenida durante 2 minutos. 

nodejs_heap_size_used_bytes{app="fundecodes-backend"} > 262144000

Significado operativo: Indica un posible memory leak o que el sistema está procesando cargas inusualmente grandes. Si no se atiende, puede derivar en un crash por Out of Memory.

Alerta 3 — SlowApiResponses (critical)

Condición: El percentil 95 de duración de las peticiones HTTP supera 2 segundos en al menos una ruta. 

histogram_quantile(
  0.95,
  sum(rate(http_request_duration_seconds_bucket{app="fundecodes-backend"}[5m]))
  by (le, route)
) > 2

Significado operativo: El API está respondiendo lentamente. Puede indicar consultas lentas a la base de datos, N+1 queries o bloqueo del event loop de Node.js.

7. Flujo automático: Alerta → Incidente → Notificación

Cuando una alerta pasa al estado Firing en Grafana, el siguiente flujo se ejecuta automáticamente:

  1. Grafana envía un webhook a POST http://localhost:4000/api/webhooks/alert con los datos de la alerta en formato JSON.
  2. El backend extrae la severidad de la alerta:
    • critical → Urgencia 1 en ServiceNow
    • warning → Urgencia 2 en ServiceNow
  3. El backend crea un incidente en ServiceNow con los campos:
    • Short description: [Fundecodes] <título de la alerta>
    • Category: Software / Application
    • Assignment group: Service Desk
  4. Simultáneamente, el backend envía un mensaje al canal de MS Teams con el título, descripción y severidad de la alerta.

8. Simulación de carga y reproducción de incidentes

El script observability/load-test/load-test.js permite generar carga controlada para activar las alertas y observar su impacto en los dashboards.

8.1 Modos disponibles

ModoComandoQué provoca
normal node load-test.js Tráfico moderado (30 req/s, 60s). Sin alertas.
stress node load-test.js --mode stress --rps 150 --duration 120 Carga alta que dispara SlowApiResponses y HighHeapMemoryUsage.
error node load-test.js --mode error --rps 50 --duration 60 Genera errores 404/401 que disparan HighHttpErrorRate.

8.2 Pasos para reproducir el incidente

  1. Verificar que el backend está corriendo: 
    curl http://localhost:4000/healthz
  2. Abrir Grafana (http://localhost:3001) en el dashboard Fundecodes Backend para observar las métricas en tiempo real.
  3. Desde la carpeta observability/load-test/, lanzar la carga de estrés: 
    node load-test.js --mode stress --rps 150 --duration 120
  4. Observar en Grafana cómo los paneles de latencia y memoria superan sus umbrales (aproximadamente entre 1 y 3 minutos tras iniciar la carga).
  5. Una vez que la alerta pase a estado Firing, verificar:
    • El incidente creado en ServiceNow.
    • La notificación en el canal de MS Teams.
  6. Detener el script cuando termine (o con Ctrl+C). Las métricas se recuperarán y la alerta pasará a estado Normal en 1-2 minutos.

9. Simulación final automatizada (demo.js)

Para la presentación final, el script observability/demo/demo.js ejecuta el flujo completo de forma automática y guiada: 

cd observability/demo
node demo.js

El script ejecuta los siguientes pasos en secuencia:

PasoDescripciónDuración aprox.
1Verificación del stack (backend, Prometheus, Grafana)~10s
2Tráfico normal (baseline a 5 req/s)30s
3Carga de estrés (120 req/s)90s
4Espera y verificación de alertas en Grafanahasta 2 min
5Creación de incidente en ServiceNow + notificación Teams~10s
6Periodo de recuperación30s
7Resolución del incidente en ServiceNow~5s

Para ajustar la carga sin modificar el script, usar el parámetro --rps: 

node demo.js --rps 80

10. Resolución de problemas del stack de observabilidad

SíntomaCausa probableSolución
Prometheus no recolecta métricas del backend host.docker.internal no resuelve en Linux Agregar al servicio prometheus en docker-compose.yml: extra_hosts: ["host.docker.internal:host-gateway"] (ya está incluido en la configuración actual)
Las alertas no llegan a ServiceNow Variables de entorno del backend no configuradas Verificar SERVICENOW_INSTANCE, SERVICENOW_USER y SERVICENOW_PASSWORD en el .env del backend
Las notificaciones no llegan a Teams TEAMS_WEBHOOK_URL no configurado o expirado Regenerar el webhook en Power Automate y actualizar TEAMS_WEBHOOK_URL en el .env del backend
Grafana muestra "No data" en los paneles El datasource de Prometheus no está conectado Ir a Connections → Data sources → Prometheus y hacer clic en Save & test
Las alertas no pasan a Firing aunque la carga es alta El backend no está siendo apuntado correctamente por Prometheus Verificar en Prometheus (http://localhost:9090/targets) que el target fundecodes-backend esté en estado UP
El script demo.js falla en el Paso 1 Algún servicio no está levantado Ejecutar primero el backend (npm run start:dev) y el stack Docker (docker compose up -d), luego ejecutar node demo.js
