Observabilidad, Alertas y Gestión de Incidentes — Fundecodes Digital

Este artículo describe el stack completo de observabilidad del sistema Fundecodes Digital, incluyendo la recolección de métricas con Prometheus, la visualización en Grafana, las tres alertas configuradas, la integración automática con ServiceNow y las notificaciones a MS Teams. También explica cómo reproducir un incidente controlado con los scripts de carga y cómo ejecutar la simulación final automatizada.

2. Arquitectura del sistema de observabilidad

El flujo completo de observabilidad funciona de la siguiente manera:

  1. El backend NestJS expone métricas en GET /metrics (formato Prometheus, usando prom-client).
  2. Prometheus hace scraping de esas métricas cada 15 segundos desde host.docker.internal:4001.
  3. Grafana consulta Prometheus para mostrar dashboards en tiempo real.
  4. Cuando una alerta supera su umbral, Grafana la evalúa y la pasa a estado Firing.
  5. Grafana envía un webhook a POST http://localhost:4001/api/webhooks/alert del backend.
  6. El backend procesa la alerta en paralelo:
    • Crea un incidente en ServiceNow via REST API (/api/now/table/incident).
    • Envía una notificación al canal de MS Teams via Power Automate.

7. Alertas configuradas

El sistema tiene tres alertas definidas en alerts.yml y provisionadas automáticamente en Grafana:

Alerta 1 — HighHttpErrorRate (warning)

Condición: Más del 10% de las peticiones HTTP retornan errores (4xx o 5xx) durante al menos 1 minuto. 

(
  sum(rate(http_errors_total{app="fundecodes-backend"}[2m]))
  /
  sum(rate(http_requests_total{app="fundecodes-backend"}[2m]))
) > 0.10

Significado operativo: Indica que el sistema está rechazando o fallando al procesar una fracción significativa del tráfico. Puede ser causado por un bug, una ruta inexistente o sobrecarga del servidor.

Alerta 2 — HighHeapMemoryUsage (warning)

Condición: El heap de Node.js supera 250 MB de forma sostenida durante 2 minutos. 

nodejs_heap_size_used_bytes{app="fundecodes-backend"} > 262144000

Significado operativo: Indica un posible memory leak o que el sistema está procesando cargas inusualmente grandes. Si no se atiende, puede derivar en un crash por Out of Memory.

Alerta 3 — SlowApiResponses (critical)

Condición: El percentil 95 de duración de las peticiones HTTP supera 2 segundos en al menos una ruta. 

histogram_quantile(
  0.95,
  sum(rate(http_request_duration_seconds_bucket{app="fundecodes-backend"}[5m]))
  by (le, route)
) > 2

Significado operativo: El API está respondiendo lentamente. Puede indicar consultas lentas a la base de datos, N+1 queries o bloqueo del event loop de Node.js.

8. Flujo automático: Alerta → Incidente → Notificación

Cuando una alerta pasa al estado Firing en Grafana, el siguiente flujo se ejecuta automáticamente:

  1. Grafana envía un webhook a POST http://localhost:4001/api/webhooks/alert con los datos de la alerta en formato JSON.
  2. El backend extrae la severidad de la alerta:
    • critical → Urgencia 1 en ServiceNow
    • warning → Urgencia 2 en ServiceNow
  3. El backend crea un incidente en ServiceNow vía REST API con los campos:
    • Short description: [Fundecodes] <título de la alerta>
    • Category: Software / Application
    • Assignment group: Service Desk
  4. Simultáneamente, el backend envía un mensaje al canal de MS Teams con el título, descripción y severidad de la alerta.

9. Configuración de ServiceNow

Para que la integración automática funcione, la instancia de ServiceNow debe estar configurada correctamente. A continuación se describen los pasos realizados:

9.1 Variables de entorno requeridas en el backend

En el archivo .env del backend (repositorio KB0001) configurar:

# ServiceNow
SERVICENOW_INSTANCE=https://<tu-instancia>.service-now.com
SERVICENOW_USER=admin
SERVICENOW_PASSWORD=<contraseña-de-la-instancia>

9.2 Deshabilitar reglas de negocio lentas (solo instancias de desarrollador)

Las instancias de desarrollador de ServiceNow tienen un límite de 30 segundos por transacción REST. Si la instancia tiene muchas reglas de negocio activas, los inserts pueden agotarse. Para solucionarlo, se pueden deshabilitar las reglas innecesarias desde el menú System Definition → Business Rules, filtrando por tabla incident y deshabilitando las que ejecutan lógica asíncrona pesada.

9.3 Verificar la integración con el script de prueba

# Desde la raíz del repositorio de observabilidad:
$env:SERVICENOW_INSTANCE="https://<tu-instancia>.service-now.com"
$env:SERVICENOW_USER="admin"
$env:SERVICENOW_PASSWORD="<contraseña>"
node servicenow/test-servicenow.js

Si todo está correcto, la salida debe mostrar:

📡  Creando incidente de prueba en https://<tu-instancia>.service-now.com…
✅  Incidente creado:
    Número   : INC0010001
    ID       : abc123...
    Estado   : 1
    Resumen  : Fundecodes TEST - Alerta alta tasa de errores HTTP
    URL      : https://<tu-instancia>.service-now.com/incident.do?sys_id=abc123

🔔  Simulando webhook de Grafana al backend local…
✅  Backend procesó la alerta: {"message":"Alert processed","incidentNumber":"INC0010001"}

🔧  Resolviendo incidente abc123…
✅  Incidente resuelto correctamente.

🎉  Prueba completa.

9.4 Ver incidentes en ServiceNow

Los incidentes creados por Fundecodes se pueden ver en:

  • Todos los incidentes: https://<tu-instancia>.service-now.com/incident_list.do
  • Solo incidentes de Fundecodes: https://<tu-instancia>.service-now.com/incident_list.do?sysparm_query=short_descriptionLIKEFundecodes
  • Incidentes resueltos/cerrados: https://<tu-instancia>.service-now.com/incident_list.do?sysparm_query=state=6^ORstate=7
Nota: Por defecto la lista de incidentes solo muestra activos (state < 6). Para ver todos, quitar el filtro "Active = true" haciendo clic en la X que aparece en la barra de filtros superior.

10. Simulación de carga controlada (load-test.js)

El script load-test/load-test.js permite generar carga controlada para activar las alertas y observar su impacto en los dashboards.

10.1 Modos disponibles

ModoComandoQué provoca
Normal node load-test/load-test.js Tráfico moderado (30 req/s, 60s). Sin alertas.
Stress node load-test/load-test.js --mode stress --rps 150 --duration 120 Carga alta que puede disparar SlowApiResponses y HighHeapMemoryUsage.
Error node load-test/load-test.js --mode error --rps 50 --duration 60 Genera errores 404/401 que disparan HighHttpErrorRate.

10.2 Pasos para reproducir el incidente manualmente

  1. Verificar que el backend y el stack de observabilidad están corriendo: 
    # Backend: debe responder con {"status":"ok"}
Invoke-WebRequest -Uri http://localhost:4001/healthz | Select-Object -ExpandProperty Content

# Prometheus: debe responder OK
Invoke-WebRequest -Uri http://localhost:9090/-/healthy | Select-Object -ExpandProperty Content

# Grafana: debe responder con {"commit":"...","database":"ok",...}
Invoke-WebRequest -Uri http://localhost:3001/api/health | Select-Object -ExpandProperty Content
  2. Abrir Grafana (http://localhost:3001) en el dashboard Fundecodes Backend para observar las métricas en tiempo real.
  3. Desde la raíz del repositorio de observabilidad, lanzar la carga de estrés: 
    node load-test/load-test.js --mode stress --rps 150 --duration 120
  4. Observar en Grafana cómo los paneles de latencia y memoria superan sus umbrales (aproximadamente entre 1 y 3 minutos tras iniciar la carga).
  5. Una vez que la alerta pase a estado Firing, verificar en ServiceNow el incidente creado y la notificación en el canal de MS Teams.
  6. Detener el script cuando termine (o con Ctrl+C). Las métricas se recuperarán y la alerta volverá a Normal en 1-2 minutos.

11. Simulación final automatizada (demo.js)

Para la presentación final, el script demo/demo.js ejecuta el flujo completo de forma automática y guiada en ~5 minutos: 

node demo/demo.js

El script ejecuta los siguientes pasos en secuencia:

PasoDescripciónDuración aprox.
1Verificación del stack (backend, Prometheus, Grafana)~10s
2Tráfico normal (baseline a 5 req/s) — muestra métricas normales30s
3Carga de estrés (120 req/s por defecto) — sube las métricas90s
4Espera y verificación de alertas activas en Grafanahasta 2 min
5Dispara webhook → crea incidente en ServiceNow + notificación Teams~10s
6Periodo de recuperación — métricas vuelven a la normalidad30s
7Resolución automática del incidente en ServiceNow~5s

Para ajustar la intensidad de la carga sin modificar el script, usar el parámetro --rps: 

# Carga más baja (apta para equipos con menos recursos)
node demo/demo.js --rps 80

# Omitir verificación inicial si el stack ya está levantado
node demo/demo.js --skip-checks

13. Resolución de problemas del stack de observabilidad

SíntomaCausa probableSolución
Prometheus no recolecta métricas (target DOWN) host.docker.internal no resuelve o el backend no está corriendo en el puerto 4001 1. Verificar que el backend corre: Invoke-WebRequest http://localhost:4001/metrics
2. En Linux, agregar al servicio prometheus en docker-compose.yml: extra_hosts: ["host.docker.internal:host-gateway"] (ya incluido en la configuración actual)
Las alertas no crean incidentes en ServiceNow Variables de entorno del backend no configuradas correctamente Verificar en el .env del backend: SERVICENOW_INSTANCE, SERVICENOW_USER y SERVICENOW_PASSWORD. Reiniciar el backend después de cambiar el .env.
Error "Transaction cancelled: maximum execution time exceeded" en ServiceNow Las instancias de desarrollador tienen un límite de 30s por transacción Ir a ServiceNow → System Definition → Business Rules → filtrar por tabla incident → deshabilitar las reglas asíncronas más pesadas.
Las notificaciones no llegan a Teams TEAMS_WEBHOOK_URL no configurado o expirado Regenerar el webhook en Power Automate y actualizar TEAMS_WEBHOOK_URL en el .env del backend. Reiniciar el backend.
Grafana muestra "No data" en todos los paneles El datasource de Prometheus no está conectado Ir a Grafana → Connections → Data sources → Prometheus → hacer clic en Save & test
Las alertas no pasan a Firing aunque la carga es alta Prometheus no está scrapeando el backend Verificar en http://localhost:9090/targets que el target fundecodes-backend está en estado UP. Si está DOWN, verificar que el backend corre en el puerto 4001.
El script demo.js falla en el Paso 1 Algún servicio no está levantado Levantar el stack en orden:
1. docker compose up -d (en el repo de observabilidad)
2. npm run start:dev (en el repo del backend)
3. node demo/demo.js
Node.js crash con "Assertion failed: UV_HANDLE_CLOSING" en Windows Bug de Node.js en Windows con el módulo fetch nativo en conexiones asíncronas Los scripts test-servicenow.js y demo.js ya usan https.request en lugar de fetch para evitar este problema. Verificar que no se estén usando versiones antiguas de los scripts.
